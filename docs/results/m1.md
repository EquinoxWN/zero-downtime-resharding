# M1 test results

Recorded 2026-10-06 on the author's machine (Intel Core i7-13700H, Windows 11, Go 1.25.6,
PostgreSQL 17.5 started by embedded-postgres v1.34.0, pgx v5.11.0). CI re-runs everything with
Go 1.26 on Ubuntu, where the same library starts PostgreSQL.

## Tests: 17 passed, 0 failed

Command: `make test`. The integration tests start three real PostgreSQL 17 servers (a control
database and two shards) on localhost; on this machine that takes about a minute, the tests
themselves about six seconds.

| Package | Tests | What it proves |
|---|---|---|
| `internal/shardmap` | 5 | Lookup returns the serving shard (a moving tenant is still served by its source); eight kinds of inconsistent map are refused; Clone is deep; every update bumps the version and an invalid one is never stored; twenty concurrent writers lose no update |
| `internal/router` | 3 | Tenants are routed by the map and requests without a tenant are refused; a newly added tenant is found without waiting for the cache to expire; an expired cache is re-read |
| `internal/move` | 2 | The publication is filtered to exactly one tenant on every table; the connection details in `CREATE SUBSCRIPTION` are quoted for libpq and again as one SQL literal (a password with a quote and a backslash cannot break out) |
| `internal/schema` | 1 | Only plain lowercase table names become SQL identifiers |
| `internal/integration` (PostgreSQL 17) | 6 | The map lives in the control database and a stale compare-and-swap conflicts; the router sends each tenant to its shard with `app.tenant_id` set; a move copies exactly one tenant (2,050 rows) and then streams inserts, updates and deletes until counts and checksums match, while another tenant's writes never reach the target; four writers committing about 7,500 transactions during a 20,000-order move lose none and duplicate none; unknown tenant, same shard, unknown shard, a second concurrent move and a target that already holds the tenant's rows are refused and leave nothing behind; abort removes the subscription, replication slot, publication and copied rows, twice in a row |

Lint: `gofmt` and `go vet` clean. Audit: `govulncheck` found GO-2026-5970 in
`golang.org/x/text` v0.29.0 (pulled in through pgx), fixed by requiring v0.39.0. The remaining
reports are all in the local Go 1.25.6 standard library and fixed in later patch releases; CI
builds with Go 1.26.

### What the numbers say

- **The copy does not stop the tenant.** While 200,000 orders were copied and streamed, four
  workers kept committing through the router: about 35,000 transactions, none failed, p99 latency
  1.2 ms. The source keeps serving the tenant until the M2 cutover.
- **The snapshot copy is quick; the stream decides the cutover.** The copy took 1.7 s. Under
  roughly 7,000 transactions per second the lag hovered between 20 KB and 570 KB of WAL, and it
  fell to 0 bytes within moments of the writers stopping. M2's write fence waits for exactly that
  moment, so its pause should be a few hundred milliseconds.
- **Exactly one tenant moved.** Both tables of tenant 3 have the same row count and md5 on both
  shards; no row of tenants 1, 2 or 4 (which share the source shard) reached the target.
- **Not measured yet:** the cutover pause and client retries (M2), and error rate and p99 under
  k6 load (M3).

## Quality control (DMAIC)

| Phase | This repository |
|---|---|
| Define | Moving a tenant to another PostgreSQL shard usually means downtime, and it is hard to prove nothing was lost; this affects teams whose database is outgrowing one machine. M1 counts when a versioned shard map changes only by compare-and-swap, a router sends each tenant to its shard, a move copies one tenant with a row-filtered publication and a copying subscription while it keeps writing, unsafe moves are refused, abort leaves nothing behind, and a verifier compares counts and md5 checksums ([RFC 0001](../rfc/0001-design.md)). |
| Measure | `make test` (6 integration tests on three real PostgreSQL 17.5 servers), `make demo`, gofmt, `go vet` and `govulncheck` on an Intel Core i7-13700H with Windows 11 and Go 1.25.6, plus two injected bugs. 17 tests passed, 0 failed; in the demo, 34,892 transactions committed during a 200,000-order move with 0 failed and p99 1.2 ms, the snapshot copy took 1.66 s, lag stayed between about 20 KB and 570 KB of WAL and fell to 0 bytes after writes stopped. |
| Analyze | Counts and checksums of tenant 3 matched on both shards and 0 rows of other tenants reached the target; removing the row filter or the snapshot copy made the integration tests fail. One defect was found: `govulncheck` reported GO-2026-5970 in `golang.org/x/text` v0.29.0, pulled in through pgx. The cutover pause and k6 error rate are not measured yet (M2, M3). |
| Improve | The module now requires `golang.org/x/text` v0.39.0, which fixes GO-2026-5970; the remaining local reports are in the Go 1.25.6 standard library, and CI builds with Go 1.26. |
| Control | The `ci` workflow's `build` job runs `make ci` (gofmt, `go vet`, the 17 tests including the integration suite on real PostgreSQL, and the demo) and `make audit` (`govulncheck`) on every push and pull request. In the code, map updates are validated and written only if the version is unchanged, twenty concurrent writers lose no update, tenant ids are integers and table names must be plain identifiers, subscription connection details are quoted twice, and test servers listen on localhost with a per-run password. |
